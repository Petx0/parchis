# Parchís RL Project — Full Code Review & Rebuild Recommendations

## Context

This is a full architectural/code review of the `parchis/` codebase (game engine, RL environment, visualization, training scripts), done to identify what should be rebuilt vs. refactored vs. left alone, in service of **maximum clarity**.

Three domains were reviewed in depth (every line read, not skimmed) against the documented spec in `docs/`, and the most severe claims below were independently re-verified by hand-tracing the code:

1. **Game engine** — `parchis/game/{game,board,piece,player,dice}.py` vs `docs/RULES.md`
2. **RL environment** — `parchis/rl/{env,env_selfplay}.py`, `parchis/evaluation/evaluate.py` vs `docs/REWARD_STRUCTURE.md`, `docs/README_ENVIRONMENT.md`
3. **Visualization & training scripts** — `parchis/visualization/*`, `parchis/training/*` (7 scripts), `parchis/utils/logger.py` vs `docs/VISUALIZATION.md`, `docs/TRAINING_GUIDE.md`

**Headline result: this is not a "clean up the style" review.** All three domains contain genuine, silent correctness bugs — not just clarity problems — several severe enough that they likely invalidate prior training/evaluation results. Two of the game-engine bugs and the self-play bug below were independently re-traced by hand against `docs/RULES.md` and confirmed true, not just plausible.

Status:
- **Domain A (game engine) is fully closed out.** All three movement bugs are fixed, the dead code is removed, and the full "Rebuild target" for domain A has been carried out: `parchis/game/game.py` is now a turn/bonus orchestrator only; move-legality logic lives in a new stateless `RuleEngine` (`parchis/game/rules.py`); capture logic is unified in `Board` (`Board.enter_piece` alongside `Board.move_piece`, no more split between `Board`/`Game`); rule-critical magic numbers are named constants (`parchis/game/constants.py`); the ad-hoc `turn_info`/`move_info` dicts are now typed dataclasses (`parchis/game/records.py`: `MoveInfo`, `RollEntry`, `TurnInfo`); and presentation (`format_game_state`/`format_turn_info`) moved to `parchis/game/formatting.py`. `Game` keeps thin delegating wrapper methods (`get_legal_moves`, `get_blockades`, etc.) so no external caller (tests, `parchis/rl/env.py`, `parchis/rl/env_selfplay.py`, `parchis/utils/logger.py`) needed to change its call sites, only its attribute access on the now-typed records. The three-sixes home-column exception ambiguity noted below was reviewed and resolved as **not a bug**: "home columns are capture-free" governs opponent captures-by-landing, a different mechanism from the three-sixes penalty (a rule-mandated forfeiture), so the existing narrow (transition-only) protection is correct as documented in `docs/RULES.md` Exception 2. All 15 tests in `test_game.py` pass (including 3 new regression tests for the fixed bugs), a 200-game stress test completes cleanly, and `parchis/rl/env.py`/`env_selfplay.py` were smoke-tested end-to-end against the new `MoveInfo` dataclass.
- **Priority 2 (self-play) is fully fixed.** `ParchisEnv` (`parchis/rl/env.py`) now takes an `opponent_policy_fn` constructor hook (default: uniform-random, preserving prior behavior) and both the regular-move auto-play loop and `_auto_play_bonus` call it instead of hardcoding `player.choose_move(...)`. `ParchisSelfPlayEnv` (`parchis/rl/env_selfplay.py`) was rewritten from scratch as a thin wrapper that passes a model-backed policy (`self._choose_opponent_move`) into that hook and no longer has its own opponent loop at all — the dead-code bug and the `env.py`/`env_selfplay.py` duplication (both flagged in the original review) were the same root cause and are both eliminated by this one change. External API surface (`env.base_env`, `env.update_opponent_model(...)`, constructor args) is unchanged, so `train_selfplay.py` and `evaluate.py` needed no edits. Verified: 3 new regression tests in `parchis/tests/test_selfplay.py` (using a call-counting fake model) prove the model is now actually consulted for both regular and chained bonus opponent moves — these tests would have failed against the old code; a real (untrained) `MaskablePPO` model was also run end-to-end through the fix outside the test suite, confirming 184 real `predict()` calls were used for opponent decisions across a 64-step episode.
- **Stale checkpoints removed.** Every checkpoint under `models/` was trained against an older, incompatible observation space (315-dim vs. the current 324-dim for 4 players) and failed to load against the current `env.py`. Since all of it predated the domain A / self-play fixes above, the user had `models/` and `logs/` (checkpoints, TensorBoard logs, and game replay JSONs) cleared out entirely rather than kept around as unusable artifacts. Both directories now exist empty, ready for fresh runs under the fixed code.
- **Priority 3 (observation double-count bug + reward doc drift) is fully fixed.** The documented bug (`env.py`'s progress-score block double-counting finished pieces, `progress` up to `2.0` against a declared `high=1.0`) is fixed — that block now just calls the already-correct `_calculate_normalized_progress()` instead of re-deriving the formula. **A second, previously-undocumented instance of the same root problem was found and fixed while adding regression tests**: the board-state channel (the num_players×76 "what's on each square" block) independently looped over `player.pieces` without excluding finished pieces, so whenever 2+ of a player's pieces finished (a completely normal end-of-game state, not an edge case), it over-accumulated at the position-76 index — up to `2.0` with all 4 pieces finished. Verified with 2 new tests in `parchis/tests/test_observation.py`, plus a ~60,000-step / ~700-game stress test across 2/3/4-player configs confirming the observation never leaves `[0.0, 1.0]`. Also cleaned up the remaining bare `76` literals in `env.py` flagged in domain B (now `Board.FINAL_POSITION`) since they were directly implicated in both bugs. `docs/REWARD_STRUCTURE.md` and `docs/README_ENVIRONMENT.md` were rewritten to match the actual current reward/observation implementation (three `reward_type`s, turn-cycle timing, the `opponent_weight` term, corrected observation layout, corrected import paths) instead of describing a reward function and observation space that were never what the code computed.

Verified: 3 new regression tests (`parchis/tests/test_agent_seat_and_seed.py`) confirm the agent occupies more than one seat across 200 resets, that the same seed reproduces the same seat, and that the same seed reproduces the same dice-roll sequence; real short training + evaluation runs (200 timesteps) were smoke-tested end-to-end through `evaluate_agent` (plain and self-play), `common.evaluate_model` (plain and self-play), all producing sane, non-degenerate win/loss splits.

Fixed by rebuilding the coordinate system around the real board topology: one quadrant's 17-cell offset template (edge run → arm dive toward center → quadratic-Bézier return to the next quadrant, routed around that quadrant's corner circle) is generated once and rotated 90° three times to cover all four colors, anchored against the game engine's real constants (`Board.STARTING_POSITIONS`, `Board.HOME_ENTRY_POINTS`) rather than hand-transcribed from the reference photo. Each color now gets its own private 8-cell home-lane coordinate table (`home_coords[color]`) instead of sharing the main-track dict; `_draw_home_columns`, `_draw_piece_on_board`, and `highlight_move` all resolve through a new `_lookup_coords` helper that picks the right table based on whether a position is on the main track or in a home column. Verified: 6 new geometry regression tests in `parchis/tests/test_visualizer.py` (board-bounds, 68 distinct main-track positions, per-color-distinct home lanes, no cell overlapping a corner's base circle, each color's start square nearest its own corner, home-entry points genuinely central) all pass; several real mid-game snapshots were rendered and visually inspected against `docs/images/foto_parchis.png` to confirm the board now reads as an authentic interrupted cross topology; the priority-5 figure-leak regression check was re-run after these edits (a full 298-turn, 4-player replay) and still shows exactly 1 open figure, confirming that fix wasn't disturbed.

## Top 5 findings, ranked by impact (all independently verified)

### 1. Self-play has never worked — models trained "against themselves" actually trained against random play — ✅ RESOLVED
`parchis/rl/env.py:294-329` (inside `ParchisEnv.step()`) already contains a full auto-play loop that random-plays opponents (players 1–3) until control returns to player 0, *before* `step()` ever returns. `ParchisSelfPlayEnv.step()` (`parchis/rl/env_selfplay.py:86-93`) calls `self.base_env.step(action)` first, then guards its own opponent-interception loop with `while self.base_env.game.current_player_idx != 0: ...` — a condition that by construction is always `False` when execution reaches it, since the base env's loop has already run to completion. **Verified by hand-tracing both files**: `_choose_opponent_move()` and therefore `self.opponent_model.predict(...)` are unreachable dead code.

**Fix applied**: `ParchisEnv` now accepts an `opponent_policy_fn` constructor argument (default: random, matching prior behavior) and its one auto-play loop — including chained bonus moves via `_auto_play_bonus` — calls it instead of hardcoding `player.choose_move(...)`. `ParchisSelfPlayEnv` no longer has any opponent loop of its own; it just passes a model-backed policy function into that hook. Verified with 3 new tests (`parchis/tests/test_selfplay.py`) using a call-counting fake model, and independently with a real (untrained) `MaskablePPO` model run manually: 184 real `predict()` calls were used for opponent decisions across a 64-step episode. Every existing self-play model checkpoint under `models/` was trained under the old broken code and is therefore effectively a random-opponent run; see the new observation-space-mismatch finding in Status above regarding reusing those checkpoints going forward.

Impact: `train_selfplay.py`, `evaluate.py --opponent <model>`, and every `models/parchis_selfplay_*` checkpoint in this repo were trained/evaluated against a uniformly random opponent, indistinguishable from `train_ppo.py`. Any claim of self-play improvement from these runs should be treated as unverified.

### 2. Home-column entry is broken in three independent ways (`parchis/game/game.py`) — ✅ RESOLVED
- **Off-by-one overshoot** (`_calculate_new_position`, line 321): `home_pos = Board.HOME_COLUMN_START + remaining_steps` should be `... + remaining_steps - 1`. **Verified by hand-trace**: Yellow at position 67 (home entry = 68, `HOME_COLUMN_START` = 69) rolling a 2 should land on 69 (67→68→69); the code computes 70. Every main-track→home-column transition — i.e. every 1–6 roll, the 7-square roll, and 10/20-square bonuses — is one square too far, and legitimate exact-landing finishes onto square 76 get silently rejected as illegal.
- **Pieces parked exactly on their home-entry square can never enter home again.** When a piece lands exactly on its entry point (0 remaining steps), the code intentionally leaves it on the main track at that square (line 330). But the very next roll simulates forward from that square, wraps past `MAIN_TRACK_SIZE`, and never re-checks `pos == home_entry_point` for the square it started on. **Verified by hand-trace**: a piece at position 68 (Yellow's own entry point) rolling a 1 computes position 1, permanently stuck circling the main track. This piece can only recover by being captured back to base.
- **Blockade-crossing is not checked for moves that end in the home column** (`path_crosses_blockade`, lines 129-171): `steps_needed` is only set for main-track destinations; for home-column destinations it stays `0`, so the loop's break condition fires after checking just the *one* square immediately after the start position, ignoring the rest of the path. A 20-square bonus or long roll can legally jump straight over a same-color blockade sitting near a player's own home stretch — a direct violation of the documented blockade rule.

Impact: these three interact — home-column entry (arguably the single most rule-sensitive mechanic in Parchís) is close to non-functional. This should have been caught by tests but wasn't (see #4).

### 3. Reward function is undocumented / three sources disagree — ✅ RESOLVED
`docs/README_ENVIRONMENT.md` describes fixed-magnitude rewards (+100 win, -100 loss, +10 finish, +5 capture, -5 invalid, -0.1 time) that don't exist anywhere in `env.py`. `docs/REWARD_STRUCTURE.md` describes a simple per-step `progress_delta` with no opponent term, explicitly framed as "removing opponent noise" — but the actual default reward (`env.py:344`, `my_delta - opponent_weight * avg_opp_delta`, α=0.5) reintroduces exactly that term, computed at turn-cycle boundaries rather than per step. Only the class docstring in `env.py` matches the code. Anyone tuning `opponent_weight` from the docs is tuning against a description of a reward function that isn't running.

**Fix applied**: both docs rewritten from scratch to describe the actual reward structure (all three `reward_type`s, turn-cycle timing, the `opponent_weight` term, and the corrected observation layout/import paths). `REWARD_STRUCTURE.md` keeps a short "History" note explaining what the old description got wrong rather than silently erasing that context.

### 4. The test suite is largely not running, and it's exactly the tests that would have caught #1/#2 — ✅ RESOLVED
Confirmed by attempting collection: **9 of ~21 test files fail to import** across `parchis/tests/` — stale references to a pre-refactor flat layout (`parchis.env`, `parchis.board`, `parchis.player`, `parchis.train_ppo`) instead of the current `parchis.rl.env`, `parchis.game.board`, `parchis.game.player`, `parchis.training.train_ppo`. `test_game.py::test_blockades` additionally calls `game.get_blockades(player.color)` against a method that takes no arguments — `TypeError`. `test_env.py` asserts an observation shape (`len(obs) == 315`, fixed 4×77 layout) that bears no resemblance to the current dynamic layout. A bare `pytest parchis/tests/` currently **aborts collection outright** rather than reporting a clean pass/fail — this is worse than "some tests fail," it silently hides that the suite isn't running at all, which is almost certainly why bugs #1/#2 were never caught.

**Fix applied**: all import-path and stale-assertion issues fixed (`test_game.py`'s issues were fixed earlier as part of domain A). Two of the five broken RL-side files (`test_training_simple.py`, `test_eval_issue.py`) turned out to be module-level debug scripts with no assertions rather than real tests — both converted into fast, assertion-based `test_` functions instead of just import-patched. See Status above for full details. `pytest parchis/tests/` now collects and passes cleanly (33 tests, ~2.5s).

### 5. Seven training scripts, ~70% duplicated, already drifting in observable ways
`mask_fn` is copy-pasted verbatim 6+ times; `make_env()` is reimplemented 3 times with mutually exclusive extra knobs (`train_ppo.py` supports `opponent_weight` but not `reward_type`; `experiment_grid.py` supports `reward_type` but not `opponent_weight` — **there is no single entry point that can combine both reward-shaping options**); `ProgressLoggingCallback` and an evaluation loop are each reimplemented 3 times. This has already produced real bugs, not just duplication risk: `train()`'s function-default `gamma=0.995` disagrees with the CLI's `argparse` default of `0.99` in the same file (`train_ppo.py:99` vs `:402`). Separately, nearly every command in `docs/TRAINING_GUIDE.md` and `docs/VISUALIZATION.md` is wrong (wrong module paths, wrong flag names, wrong default values, wrong description of what `train_quick.py` actually does) — a new user following either doc verbatim cannot get past the first command.

## Full findings by domain

### A. Game engine (`parchis/game/`) — ✅ RESOLVED (see Status above)

Original finding, for reference: `board.py`, `piece.py`, `dice.py`, `player.py` were small, single-purpose, and clean — no rebuild needed. `game.py` (729 lines) was a god object combining four responsibilities with no boundary between them: pure rule/legality computation, state mutation, turn/bonus orchestration, and text presentation.

All of the following were fixed/resolved:
- **Capture logic in two places with different rules** — `Board.move_piece` and `Game._execute_entry_move` implemented separate capture algorithms. Fixed: both now live in `Board` (`Board.move_piece` and the new `Board.enter_piece`), so `Game` no longer contains any capture logic itself.
- **Dead/vestigial code** — the byte-identical `if/else` at old `game.py:270-275` and the unread `turn_info['penalty_no_bonus']` were both removed.
- **No named constants** — `ENTRY_ROLL`, `BONUS_TURN_ROLL`, `ALL_OUT_BONUS_ROLL`, `THREE_SIXES_LIMIT`, `CAPTURE_BONUS_SQUARES`, `FINISH_BONUS_SQUARES` now live in `parchis/game/constants.py`; the stacking cap is `Board.MAX_PIECES_PER_SQUARE`.
- **`turn_info` as an ad-hoc untyped dict** — replaced with typed dataclasses in `parchis/game/records.py` (`MoveInfo`, `RollEntry`, `TurnInfo`), consumed via attribute access everywhere (`game.py`, `utils/logger.py`, `rl/env.py`, `rl/env_selfplay.py`, tests). The JSON log schema written by `GameLogger.log_turn` is unchanged, so `visualizer.py` (which only reads that JSON, never the live objects) needed no changes.
- **Three-6s home-column exception ambiguity** — reviewed and resolved as not a bug: "home columns are capture-free" (under "Capturing" in `docs/RULES.md`) governs opponent captures-by-landing; the three-sixes penalty is a distinct rule-mandated forfeiture, not a capture-by-landing, so it isn't covered by that statement. The existing narrow (transition-only) protection matches Exception 2's literal wording and was kept as-is, with a comment added at the decision point explaining why.
- **Rebuild target (the full split)** — carried out: `parchis/game/rules.py` (`RuleEngine`, stateless legality: `get_legal_moves`, `get_blockades`, `compute_path`, `path_crosses_blockade`, `calculate_new_position`) is now separate from `parchis/game/game.py` (`Game`, stateful turn/bonus orchestration only), with presentation moved to `parchis/game/formatting.py`. `Game` keeps thin delegating wrapper methods for the rule-engine queries so the external API (tests, `rl/env.py`, `rl/env_selfplay.py`) didn't need to change its call sites.

### B. RL environment (`parchis/rl/`, `parchis/evaluation/`) — self-play (#1) and observation/reward-doc bugs (#3) ✅ RESOLVED, seat/seed issues still open

- **Self-play dead code (finding #1)** — fixed. See Status above for details: `ParchisEnv` gained an injectable `opponent_policy_fn` hook used for both regular and bonus opponent moves; `ParchisSelfPlayEnv` was rewritten as a thin wrapper plugging a model-backed policy into that hook instead of re-implementing (and never reaching) its own opponent loop. This also eliminates the `env.py`/`env_selfplay.py` duplication finding (#10 below), since there is now exactly one implementation of "resolve opponent turns."
- ~~**Observation "progress" is computed twice, inconsistently, and one version can exceed its declared bound.**~~ — **fixed**, see Status above. Also caught and fixed a second instance of the same problem in the board-state channel (finished pieces over-accumulating at position 76). `docs/REWARD_STRUCTURE.md`/`docs/README_ENVIRONMENT.md` doc drift (finding #3) also fixed — both rewritten to match the actual code.

Still open (beyond self-play, the observation/reward-doc fixes, and the seat/seed fix below):
- ~~**`seed` is entirely cosmetic.**~~ — **fixed**, see "agent seat randomization + real `seed` support" in Status above. `reset()` now seeds Python's global `random` module (the actual source of `Dice.roll()`/`Player.choose_move()` randomness) whenever an explicit seed is given.
- ~~**The learning agent always moves first.**~~ — **fixed**, see Status above. `ParchisEnv.agent_player_idx` is now reassigned to a uniformly-random seat every `reset()` instead of being hardcoded to index 0.
